# Reproducibility environment

What was used to produce the released results, and — equally important — what
was not recorded at run time.

## Models

| Role | Model identifier | Source |
|---|---|---|
| Primary study | `claude-opus-4-7` | Recorded in `results/robustness/human_agreement_metrics.csv` |
| Comparator | `gpt-5.4-mini` | Recorded in `results/gpt/coverage_scores.json` (`_model`) |

Both models were given the identical corpus, identical retrieved evidence and
the identical prompt (`prompts/scoring_prompt_v2.md`). The only variable between
the two runs is the model.

## Sampling parameters — not recorded

**Temperature, top-p, seed and other sampling parameters were not captured at
scoring time**, and are therefore not reported here. They are not recoverable
after the fact, and this document does not guess at them.

The practical consequence is bounded and measured rather than hypothetical: the
three-run stability analysis re-scored a subset under the same conditions and
found a mean per-report MMRI standard deviation of σ = 0.033
(`results/robustness/stability_kruns_summary.csv`). Note that this covers a
stratified subset of six reports spanning the observed range of misalignment,
not all twenty. That figure is the honest estimate of run-to-run variation, and
it is what a re-scoring attempt should be compared against.

To reproduce the *published* numbers exactly, use the released scores in
`results/` rather than re-scoring. This is a limitation of the released package,
recorded here so that anyone rerunning the pipeline knows what to expect.

For future runs, capture the sampling parameters alongside the responses.

## How scoring was invoked

Stage 2 is deliberately provider-agnostic and makes no API calls of its own:

- `stage2_score.py show <report_id> <topic>` renders one cell's prompt to stdout
- `stage2_score.py show_all` renders every cell's prompt in sequence
- the operator scores those prompts with the model of their choice and writes
  one `.response.json` per cell into `llm_scores_per_cell/`
- `stage2_score.py collect` validates the responses, joins them to the evidence,
  and writes the score tables and audit logs

That indirection is why the same prompt could be run against two different
providers without changing any code, and it means no provider SDK is required to
rerun the aggregation.

## Software

| Component | Version | Role |
|---|---|---|
| Python | 3.9.6 | interpreter (3.10+ recommended for new runs) |
| pdfplumber | 0.10.3 | text layer and table extraction |
| pytesseract | 0.3.13 | Python wrapper for the OCR engine |
| Tesseract | 5.5.2 (leptonica 1.87.0) | OCR engine, `eng` language model |
| pdf2image | installed 2026-04-20 | page rasterisation (exports no `__version__`) |
| Poppler (`pdftoppm`) | 26.04.0 | backend for pdf2image |
| matplotlib | ≥ 3.7 | figures |
| numpy | ≥ 1.24 | figures |

The Python packages and the `tesseract` binary all carry an install date of
2026-04-20, the same day extraction was run, so these are the versions that
produced the released chunks rather than a later environment.

**Division of labour.** pdfplumber performs no OCR. It reads the embedded text
layer and detects tables; the OCR path triggers only where a page yields fewer
than 200 characters of extractable text *and* contains images, so the two never
process the same page. Across the corpus this applies to 28 of 1,272 pages.

System binaries required for the OCR path only: `tesseract` and `poppler`
(`brew install tesseract poppler`, or `apt-get install tesseract-ocr
poppler-utils`).

**Version note.** The original analysis ran on Python 3.9.6. The scripts use
`from __future__ import annotations` together with PEP 604/585 type syntax, so
they import cleanly on 3.9, but 3.10 or newer is recommended for new runs.
`scripts/verify_repo.py` and `scripts/fetch_reports.py` use only the standard
library and run on either.

Versions above are those installed in the environment that produced the released
outputs. matplotlib and numpy affect only figure rendering, not any reported
value, and are given as minimum constraints.

## Determinism

| Stage | Deterministic? |
|---|---|
| 1.1 Extraction (PDF → chunks) | Yes — same PDFs give the same chunks |
| 1.2 Topic retrieval | Yes — deterministic keyword/score ranking |
| 2 LLM scoring | **No** — σ = 0.033 across 3 runs on a 6-report subset |
| 3 MMRI aggregation | Yes — pure arithmetic over the scores |
| Figures | Yes — regenerated byte-identically from the released scores |

Because stages 1 and 3 are deterministic, everything except the scoring step can
be reproduced exactly from the released data.

## Corpus provenance

The 20 source PDFs are not redistributed. `data/report_metadata.csv` records a
source URL, an access date and a SHA-256 checksum for each, and
`scripts/fetch_reports.py` re-downloads and verifies them byte-for-byte. See
`docs/CORPUS.md`.
